# Roast My Drupal — v2 Design

## Objective

Build out the features v1 explicitly deferred: a caching layer (mainly
to be a good citizen toward drupal.org's servers), per-maintained-module
health data to enrich the roast, a structured "roast card" display, and
a funnier prompt tone. No new feature categories beyond v1's own
deferred backlog — see `v1.md`'s "Cut from v1" and "Explicitly deferred"
notes in `v1-phases.md`.

## Architecture

```
[Browser: username/URL input]
        │
        ▼
[Next.js API route]
   1. Normalize input → username
   2. Check cache (Vercel KV, keyed by normalized username)
        │
        ├─ hit ──────────────────────────────┐
        │                                    │
        └─ miss                              │
             │                               │
             ▼                               │
   3. Resolve username → uid                 │
   4. Scrape: profile, contribution-records   │
      (x2), + up to 5 maintained-project      │
      pages for module health                 │
             │                               │
             ▼                               │
   5. Cache the raw scrape result             │
      (short TTL)                             │
             │◄──────────────────────────────┘
             ▼
   6. Parse + build roast input (always fresh,
      even on a cache hit)
   7. streamText with the tuned system prompt
   8. Attach the roast input's stats as a response
      header (`X-Roast-Stats`); stream the roast
      text as the body, same as v1
        │
        ▼
[Browser renders a roast card: stats from the
 header + streamed text into the card body]
```

Only the *scrape* is cached — the roast text itself is never cached, so
repeat visits to the same profile still get a fresh roast. This keeps
the caching motivation identical to v1's note: reduce redundant load on
drupal.org, not response latency or LLM cost.

## Components

- `lib/cache.ts` (new) — thin Vercel KV wrapper: `getCachedProfileData` /
  `setCachedProfileData`, keyed by normalized username, TTL ~10 minutes.
  Any KV error (unreachable, timeout, etc.) is treated as a cache miss —
  never blocks the request.
- `lib/module-health-client.ts` + `lib/parse-module-health.ts` (new) —
  fetch and parse up to the first 5 entries in `projectsMaintained`,
  fixture-tested the same way as `parse-profile.ts`. Extracts last
  release date and open issue count per project.
- `lib/build-roast-prompt.ts` (updated) — `RoastInput` gains a
  `moduleHealth: { name, lastReleaseDate, openIssueCount }[]` field;
  `SYSTEM_PROMPT` rewritten for a punchier, funnier tone (few-shot
  examples of the target joke style).
- `lib/drupal-client.ts` (updated) — `fetchDrupalProfileData` checks the
  cache first; on a miss, also fires the up-to-5 module-health fetches
  alongside the existing 3, all via `Promise.all`.
- `app/api/roast/route.ts` (updated) — attaches `X-Roast-Stats` (a
  base64-encoded JSON blob of the roast input's stats) as a response
  header before returning the streamed text body.
- `app/page.tsx` (updated) — renders a roast card: stats parsed from the
  `X-Roast-Stats` header (account age, credits, badge, module health)
  displayed alongside the streamed roast text. A missing/malformed
  header degrades to showing just the roast text, no hard error.

## Data sources — new for v2

- `/project/{name}` pages (maintained-project pages) — need to confirm
  during implementation: robots.txt allowance, and that last-release-date
  and open-issue-count actually render server-side without
  authentication. Treat this as a research step before writing the
  parser, the same way v1 researched `/u/{username}` and
  `/user/{uid}/contribution-records` before building `parse-profile.ts`.
- Vercel KV — new external dependency (`@vercel/kv`), new env vars
  (`KV_REST_API_URL`, `KV_REST_API_TOKEN`) provisioned via the Vercel
  dashboard at deploy time, not in code.

## Fields included in v2 (additions to v1's Tier 1/3)

**Tier 4 — module health (capped to the first 5 maintained projects)**
- Project name
- Last release date
- Open issue count

Capped at 5 regardless of how many projects someone maintains, so
worst-case latency and drupal.org request count stay bounded for
prolific maintainers.

## Roast tone / guardrails

- Funnier system prompt: sharper comedic direction, punchier phrasing,
  a couple of few-shot example jokes — still enforcing the
  Drupal-activity-only scope from v1 (no real name, country, or
  employer).
- Module health data is itself Drupal-activity-scoped, so it introduces
  no new personal-data risk — same guardrail as v1's existing fields.

## Output format

A structured roast card in the browser: the parsed stats (account age,
contribution credits, membership badge, module health) rendered
alongside the streamed roast text, replacing v1's plain-text-only
block. Delivered as a single HTTP response — stats in the
`X-Roast-Stats` header, roast text streamed in the body — rather than
adopting the AI SDK's full data-stream protocol. No downloadable or
shareable image (that stays a candidate for a future version).

## Error handling

- Cache miss or KV read/write failure → falls through to a live scrape,
  same as every other degrade-gracefully path in this app.
- One maintained project's health fetch fails → omit that project's
  health data, keep the others (same pattern as the existing 3-fetch
  scrape's per-field graceful degradation).
- Missing or malformed `X-Roast-Stats` header on the frontend → render
  the roast text alone, no card stats, no hard error.
- All v1 error handling (unresolved username, rate limit, LLM failure)
  is unchanged.

## Testing

- Unit tests for the new module-health parser against fixture HTML
  (a maintainer with several projects, one with none)
- Unit tests for `lib/cache.ts` against a mocked KV client (hit, miss,
  error-falls-through-to-miss)
- Manual/integration check against real usernames, exercising both a
  cache-miss and a cache-hit request for the same username

## Explicitly deferred (post-v2)

- Tier 2 activity feed — still excluded; no compliant data source was
  found in v1 or v2 research
- Caching the generated roast text itself
- Downloadable/shareable roast card image (e.g. via `@vercel/og`)
