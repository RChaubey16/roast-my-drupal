# Roast My Drupal — v1 Design

## Objective

User enters their drupal.org username or profile URL → app scrapes their
Drupal.org footprint → cleans/normalizes the data → asks an LLM (via the
Vercel AI SDK) to roast the profile, scoped strictly to their Drupal
activity (not personal details like real name, location, or employer).

## Architecture

Single Next.js app, deployed on Vercel. One API route handles the whole
pipeline server-side; the frontend is just an input box + streamed result.

```
[Browser: username/URL input]
        │
        ▼
[Next.js API route]
   1. Normalize input → username
   2. Resolve username → uid (JSON:API or api-d7)
   3. Scrape 3 pages: profile (/u/{username}),
      activity (/user/{uid}/track),
      contribution-records (/user/{uid}/contribution-records)
   4. Clean/normalize into a single structured "roast input" object
   5. Pass to Vercel AI SDK (streamText) with a system prompt
      scoped to Drupal-activity-only roasting
        │
        ▼
[Response streamed back to browser as it generates]
```

No caching in v1 — every request re-scrapes and re-roasts. Caching
(e.g. Vercel KV keyed by username, short TTL) is a planned fast-follow
once roast quality is proven out, mainly to be a good citizen toward
drupal.org's servers rather than for performance.

## Components

- `lib/drupal-client.ts` — handles the 3 fetches + uid resolution,
  returns raw scraped fragments
- `lib/parse-profile.ts` — HTML parsing (cheerio) → typed fields (bio,
  join date, org, badges, projects maintained, activity feed, credit
  count/date)
- `lib/build-roast-prompt.ts` — turns the cleaned data object into the
  prompt payload
- `app/api/roast/route.ts` — orchestrates the above, applies rate
  limiting, streams the AI response
- Rate limiting via a simple in-memory/edge counter per IP (e.g.
  `@upstash/ratelimit` in-memory mode or a bare token bucket) — no
  external DB needed for v1

## Data sources (confirmed by direct testing against drupal.org)

drupal.org is currently mid-migration from a legacy site to a new
Drupal 10 site (`new.drupal.org`), so three data surfaces coexist:

1. **New JSON:API** (`drupal.org/jsonapi/user/user?filter[name]=...`) —
   thin: display name, country, first/last name, git username, avatar.
2. **Legacy REST API** (`drupal.org/api-d7/user.json?name=...`) —
   richer: HTML bio, organizations, contribution role, websites,
   languages, country, account creation timestamp, timezone. Still
   live today but may be deprecated as the migration progresses.
3. **HTML pages** (the primary source for v1 — all plain
   server-rendered HTML, no headless browser needed):
   - `/u/{username}` — bio, "on Drupal.org for X years," org
     affiliation, badges, membership status, "Projects maintained"
     list.
   - `/user/{uid}/track` — recent activity feed: issue title, reply
     count, last-updated ("3 weeks ago" etc).
   - `/user/{uid}/contribution-records?field_is_sa_value=0` — official
     contribution-credit ledger, grouped by project, with dates, and a
     total count up front ("Displaying 1–50 of 153").

`robots.txt` sets `Crawl-delay: 10` but does not block any of the above
paths. None of the paths we need require authentication.

## Fields included in v1

**Tier 1 — profile page**
- Username / display name, join date (→ account age)
- Country / organization affiliation
- Bio text
- Membership badge status
- Projects maintained (list + count)

**Tier 2 — activity feed**
- Last activity date + type
- Sample of recent activity titles/reply counts

**Tier 3 — contribution records**
- Total contribution credit count
- Most recent credit date
- Security advisory credit count

**Cut from v1** (candidates for v2):
- Per-maintained-module health (last release date, open issue count) —
  requires a second scrape hop per maintained project
- Redundant `api-d7` fields already covered by HTML scraping

## Roast tone / guardrails

Roast content is scoped strictly to the user's Drupal activity and
public contribution footprint (bio phrasing, staleness, contribution
claims vs. reality, etc.). Personal details incidentally present in
scraped data (real name, country, employer) are not used as roast
material — enforced via system prompt.

## Output format

Plain text roast, streamed to the browser via the AI SDK's
`streamText` as it generates. Structured/visual "roast card" output is
a possible fast-follow, not part of v1.

## Error handling

- Username doesn't resolve to a uid → friendly "couldn't find that
  profile" message, no LLM call made (saves cost)
- One of the 3 scrapes fails/404s → degrade gracefully, roast with
  whatever data succeeded rather than hard-failing (e.g. someone with
  zero activity still gets roasted for having zero activity)
- Rate limit exceeded → clear "slow down" message, no scrape/LLM call
  triggered
- LLM call fails → simple error message, retry button

## Testing

- Unit tests for the HTML parsers against saved fixture HTML (so tests
  don't hit drupal.org live)
- Manual/integration check against a couple of real usernames (a
  prolific one, a near-empty one) before shipping
